# P2.10 — Workload awareness rework

> Single document covering the five fixes shipped on 2026-05-16, after a
> live audit of `predictive_preload` recall + a casual user note that the
> active-window assumption felt fragile («что-то крутится в фоне, а я в
> любом фокусном окне»). For the prior baseline see `p2.5-rollup.md`.

## TL;DR

| Layer | Before this session | After this session |
|---|---|---|
| Game classification | `steam_app_<id>` → `OTHER` | `steam_app_*`, `lutris-*`, `heroic-*` prefix → `GAME` |
| Headroom matcher | static frozenset (`RENDER ∪ GAME`) | `is_headroom_class()` — shares matcher with profile resolver |
| Browser bucket | `zen`/`firefox-dev` lived in `CODE` (`-2 %` knee) | new `Profile.BROWSER` (`+3 %` knee), headroom-eligible |
| Reactive trigger | only KNN-based `predictive_preload` (floor=0.6) | parallel `slope_preload` — fires on raw °C/s, KNN-independent |
| Focused-window bias | focused workload class wins outright | focused contributes one vote — highest-priority across focused + top_processes wins |
| Tests | 807 green | **813 green** (+2 net, +6 new tests, −1 superseded assert) |

## Narrative — what we saw, why it mattered

### The audit

`/api/predictor-cockpit` looked healthy — `throttle_prob` distribution
across 5738 decisions was 84 % calm, 5 % moderate, a 1.1 % hot tail at
`p≥0.7`. `predictive_preload` fired 47 times with valid ground truth
and `ramp_cooling` reached the asusctl actuator 70 times. The chain
was alive.

The forecast quality wasn't.

- **ME** of expected vs realised peak at h=30s: **−6.8 °C** (predictor
  systematically expected the chip hotter than it ended up).
- **Direction-correct** (peak30 ≥ now): **15 %**. Eighty-five percent
  of the time, when the predictor warned «hot pressure» the chip was
  already at its local peak and on the way down.
- **0/47** of the «hot» predictions actually crossed 85 °C in the next
  thirty seconds.
- **Recall** against `throttle_events` looked like 0/615 at first read
  — later corrected: `decisions.jsonl` only retains ~80 minutes, so
  the comparison was 0/3 within the overlap window. Still zero, just
  on a much smaller sample.

Translated: the KNN-driven preload pipeline was both noisy and slow.
It cooled phantom peaks (false-positive on cooldown ramps) and missed
the real ones (phase-shift spikes faster than its 30 s horizon).

### The two surprises in the workload breakdown

Throttle events grouped by `workload_at_start` (4 days, 615 events):

```
zen          362  (59 %)   ← browser
kitty        192  (31 %)   ← terminal
steam_app_*   23  ( 4 %)   ← actual games
others        38  ( 6 %)
```

Two findings that didn't square with the configuration:

1. The dominant heat source was a **browser**, but `zen` was sitting
   in `CODE_CLASSES` — which carries a `-2 %` knee bias («editor
   sessions should run quieter than base»). The cooling system was
   actively *subtracting* from the fan curve while the chip burned.

2. **Games never classified as games.** `workload_class=steam_app_2073850`
   (Hyprland's window class for THE FINALS) failed the exact-string
   `GAME_CLASSES` lookup and silently fell through to `OTHER`. The
   `+8 %` GAME knee bump and the `+5 %` headroom both disabled, on
   the workload they were designed for.

### The user-shaped boundary case

After fixing those two: «иногда что-то крутится фоновое, а я могу
быть в любом фокусном окне. всегда за этот вопрос переживал».

Reading the resolver confirmed the worry. `resolve_profile()` returned
the focused-window classification *outright* whenever it matched —
the `top_processes` fallback only fired when the focused window
couldn't be classified. So `ALT-TAB` from THE FINALS to a kitty
window flipped the profile from `GAME` to `CODE`, and the chip's
opinion about how hard it was working wasn't asked.

The fix below treats focused-window as one contributor among many,
and lets the highest-priority profile across all contributors win.

              │                                          │

Two policies now act on the knee in parallel:

```
   p ≥ 0.6        ┌────────────────────┐
  ─────────────▶  │ predictive_preload │  ─ KNN: pattern-match precedents
  (KNN-driven)    └────────────────────┘     for «next 30 s looks hot»
                            +
   slope > 0.3   ┌──────────────────┐
  ─────────────▶ │  slope_preload   │  ─ raw kinematics: «temperature is
  AND temp ≥ 75  └──────────────────┘     rising fast right now»
  (model-free)
```

`predictive_preload` carries the sustained-pressure case; `slope_preload`
carries the transient. They stack additively (both clamp into [0, 100]
through `_clamp`).

## Specs — file-by-file

### `coolstep/core/workload_profile.py`

```python
class Profile(str, Enum):
    CODE = "code"
    RENDER = "render"
    GAME = "game"
    BROWSER = "browser"   # NEW — split out of CODE
    IDLE = "idle"
    OTHER = "other"

GAME_CLASS_PREFIXES = ("steam_app_", "lutris-", "heroic-")   # NEW

BROWSER_CLASSES = frozenset({                                # NEW
    "zen", "firefox", "firefox-developer-edition", "librewolf",
    "chromium", "chromium-browser", "google-chrome", "brave",
    "brave-browser", "vivaldi", "qutebrowser",
})

# Removed from CODE_CLASSES: zen, firefox-developer-edition, qutebrowser.

def _classify(name):
    if name in GAME_CLASSES or name.startswith(GAME_CLASS_PREFIXES):
        return Profile.GAME
    if name in RENDER_CLASSES:   return Profile.RENDER
    if name in BROWSER_CLASSES:  return Profile.BROWSER          # NEW
    if name in IDLE_CLASSES:     return Profile.IDLE
    if name in CODE_CLASSES:     return Profile.CODE
    return None

def is_headroom_class(name):                                     # NEW (export)
    p = _classify(name.lower())
    return p in (Profile.GAME, Profile.RENDER, Profile.BROWSER)

_FALLBACK_PRIORITY = (
    Profile.GAME, Profile.RENDER, Profile.BROWSER,               # BROWSER spliced
    Profile.IDLE, Profile.CODE,
)

def resolve_profile(workload_class, top_processes=()):
    # NEW SEMANTICS: focused contributes one vote; top_processes contribute
    # the rest; highest-priority across all candidates wins.
    candidates = set()
    if workload_class:
        if (hit := _classify(workload_class.lower())) is not None:
            candidates.add(hit)
    for proc in top_processes:
        if proc and (hit := _classify(proc.lower())) is not None:
            candidates.add(hit)
    for prio in _FALLBACK_PRIORITY:
        if prio in candidates:
            return prio
    return Profile.OTHER
```

## Assumptions & open risks

1. **`top_processes` carries the heavy worker's binary name** — currently
   `hyprctl` collector takes the top 8 by CPU%. For most launches the
   process name in the tree is one of `steam`, `gamescope`,
   `wine64-preloader`, `wineserver`, all already in `GAME_CLASSES`.
   But **a standalone wine binary** (e.g. `THE_FINALS.exe` running
   without Steam) won't match — the bg-detection silently degrades.
   Mitigation deferred — see backlog.

2. **`cpu_temp_slope_per_sec_short` window length is whatever the
   fingerprint says it is** — at the time of writing this is a 3-tick
   moving slope (~600 ms at 0.2 s period). If the period changes,
   `SLOPE_TRIGGER_C_PER_SEC` may need a rescan. The threshold was
   chosen with «±0.05 °C/s when calm» observed at the current cadence.

3. **The KNN forecast quality issue is unaddressed.** `predictive_preload`
   still triggers on `throttle_prob ≥ 0.6`, and the predictor still
   has a ME of about −6.8 °C against realised peaks. The slope policy
   is *parallel* protection, not a replacement. Auto-shrinking
   `predictive_preload` amplitude against observed ME is filed in
   the backlog.

4. **`Profile.BROWSER` is a new public enum value.** Any consumer
   that hardcoded a switch over `code|render|game|idle|other` will
   silently get the OTHER branch. The dashboard renders profile as
   a free string so it's safe; CLI / other consumers may need a
   rescan.

5. **«Background wins focused» is a behaviour change**, not a bug fix.
   The previous test `test_resolve_focused_class_beats_top_processes`
   was explicitly asserting the old semantics and was removed.
   Reasoning: thermals don't care which window has keyboard focus —
   they care which process is on the CPU. If a future user *needs*
   focus-led cooling (rare — would mean «my game in fg drives cooling,
   not my background render»), a `policy=focus_first` opt-in is the
   right pattern, not a code revert.

6. **Heat-signature fallback (`OTHER` + hot chip → BROWSER`) is not
   implemented.** Today an unknown `workload_class` with no matching
   `top_processes` and a 82 °C chip stays in `OTHER` (no bump).
   Filed in backlog as the cheapest next win.
